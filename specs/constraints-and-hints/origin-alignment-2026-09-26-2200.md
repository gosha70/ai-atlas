# Origin alignment check — constraints-and-hints

Origin: https://github.com/gosha70/ai-atlas/issues/43 (child of #23; the epic's §5 and §6, read in full this session) + specs/constraints-and-hints/origin/2026-09-26-owner-decisions.md

Origin claim:
> Epic gosha70/ai-atlas#23 §5 asks to "consume Jakarta Bean Validation constraints where present on entity fields and method parameters", to "support an AI-ATLAS parameter-level override (for example @AgenticParam)", and to "normalise all of the above into the Contract IR", with criteria that "constraints on service parameters reach the MCP inputSchema", "contradictory constraints fail at compile time" and "requiredness is represented explicitly and consistently". §6 asks to "emit MCP behavioural hints such as read-only, destructive, idempotent, and open-world", with "explicit annotation values override inferred defaults" and "documentation states that behavioural hints are client guidance, not authorization"; its design constraints require that "changes that alter generated public shapes should ship behind an opt-in compatibility flag". Issue #43, created from the owner-approved draft on 2026-09-26, fixes the decisions: per-key override precedence, explicit-only hints, @Tool kept with generated tool specifications registered as SyncToolSpecification, enforcement by a @Validated generated tool class, irVersion 2 with unknown slots for migrated baselines, one flag ai.atlas.constraints, SYNC servers only.

Working claim:
> spec.md reads Bean Validation by qualified name and two new zero-dependency annotations (@AgenticParam, @AgenticConstraints) into one per-key constraint model with explicit requiredness, failing on self-contradictions and warning on looser input overrides (FR-001..004; epic §5 criteria: BV on fields and parameters, parameter override, contract may differ from persistence, contradictions fail, requiredness explicit). The model is recorded in Contract IR irVersion 2, with version-1 baselines migrated with unknown slots, and the demo baseline regenerated (FR-005..007; epic §5 "normalise into the Contract IR"; Phase 2 migration policy). The gate classifies input narrowing and new requiredness as breaking, widening as compatible, and output constraints and hints as informational, and never flags a change from an unknown slot in gate or lock mode (FR-008..011; epic §1 "narrowing an input type/constraint ... is detected", deferred from Phase 2). Behind ai.atlas.constraints, OpenAPI, REST, MCP tool classes (@Validated) and a generated mcp-tools.json carry the constraints and the explicitly declared hints, with byte-identical output when the flag is off (FR-012..017; epic §5 "reach the MCP inputSchema" and "reach OpenAPI parameter/request schemas", §6 hints explicit and never inferred, design constraint "opt-in compatibility flag"). The runtime registers every tool once through a SyncToolSpecification list applying those schemas and hints and warns when constraints are advisory; the plugin exposes the flag (FR-018..020; spike-proven, #42 preserved). Docs state hints are guidance, not authorization; the build is green on both JDKs (FR-021..022).

Collection safety, projections, REST metadata and release snapshots stay in Phases 4–5.
