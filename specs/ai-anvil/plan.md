# ai-anvil — Research & Plan

> **Status:** Draft plan for review · **Date:** 2026-08-07 · **Author:** Team Lead (Claude)
> **Working name:** `ai-anvil` (provisional — see [Naming](#naming)). Sibling to `ai-atlas`.
> **One-liner:** A deterministic Java tool that turns a natural-language data-model description into a
> Liquibase-migrated database schema and JPA/Hibernate persistence layer (entities + DAO + Service),
> using an LLM **only** for the first NL→schema step. `ai-atlas` takes over at the API layer.

---

## 1. Thesis & goal

The strategic goal (user's words): *demonstrate that an AI harness can be more efficient and less
expensive if companies invest in **deterministic tooling** around AI/vibe coding.*

`ai-anvil` is the second tool in a family of narrow, deterministic, LLM-callable Java tools:

| Tool | Input | Deterministic output | LLM role |
|------|-------|----------------------|----------|
| **ai-anvil** (this) | NL data-model description | Liquibase changelog + JPA entities + DAO + Service | NL → schema IR **only** |
| **ai-atlas** (exists) | Annotated `@AgenticExposed` services | PII-safe DTOs + MCP tools + REST + OpenAPI | none (pure compile-time) |

The two compose end-to-end: **NL → (ai-anvil) → persistence layer → annotate services → (ai-atlas) → REST/MCP/OpenAPI.**

**Core design principle (locked with user):** the LLM is confined to producing a *validated intermediate
schema representation (IR)*. Every downstream artifact — SQL/Liquibase, entities, DAO, service — is
generated by **deterministic code** (JavaPoet + Liquibase model API + an IR-diff engine). This is what
makes the output reproducible, reviewable, cheap, and the reason the thesis holds: one cheap constrained
LLM call replaces thousands of tokens of "vibe-coded" boilerplate that a harness would otherwise generate
non-deterministically on every run.

---

## 2. Decisions locked (this session)

1. **Placement:** new **standalone sibling repo** (`ai-anvil`), depends on nothing in `ai-atlas`, mirrors
   its Gradle/version-catalog/JavaPoet/`@Generated` conventions.
2. **LLM layer:** **LangChain4j** (not Spring AI). Rationale: keeps the core **Spring-free** so it runs in a
   plain CLI, a STDIO MCP process, and an IntelliJ plugin without a Spring context; first-class
   JSON-Schema-constrained structured output against **Ollama** (local) and OpenAI/Anthropic (external)
   through one `AiServices` interface.
3. **Determinism:** LLM produces the **schema IR only**; Liquibase, JPA, DAO, Service are 100% deterministic.

## 3. Research findings

### 3.1 How `ai-atlas` exposes tools (and where ai-anvil must diverge)

Verified against the repo (see agent sweep):

- ai-atlas is a **compile-time codegen framework**, not a server. Its MCP surface is provided by Spring AI's
  `spring-ai-starter-mcp-server-webmvc` **inside a host Spring Boot app**, over **SSE at
  `http://localhost:8080/sse`**. Tools are `@Tool`-annotated `@Service` methods collected by a lazy
  `ToolCallbackProvider` (`AgenticMcpConfiguration.LazyToolCallbackProvider`) to dodge an MCP autoconfig
  circular dependency.
- **There is no** standalone `main()`, no STDIO transport, no `.mcp.json`, no Claude Code hooks, no CLI, and
  **no LLM client** anywhere in ai-atlas. Its only DB-adjacent code is *reflection-only* Hibernate proxy
  unwrapping in the JSON serializer — **no JPA, no Liquibase, no JDBC**.
- **Implication:** ai-anvil's harness integration (CLI, STDIO MCP, hooks, IntelliJ) and its entire persistence
  domain are **greenfield**. We reuse *conventions* from ai-atlas (multi-module Gradle, `libs.versions.toml`
  as sole version authority, JavaPoet for all Java generation, `@Generated("ai.anvil")` on every emitted file,
  AGGREGATING-style discipline), **not code**.

### 3.2 Technical building blocks (validated)

- **NL → structured JSON, locally:** LangChain4j supports JSON-Schema-constrained output on Ollama
  (`RESPONSE_FORMAT_JSON_SCHEMA` capability / `responseSchema(...)`, GBNF grammar constraint under the hood).
  `AiServices` auto-derives the schema from the Java return type. Caveat: small local models (e.g. 1B) honor
  schemas unreliably → we validate + repair-loop and recommend a capable local model (e.g. `llama3.1`, a
  code/instruct model) with an external-provider fallback via config.
- **Schema → JPA entities, deterministically:** industry precedent exists (JPA Buddy, Hibernate Tools,
  `jpa-entity-generator`) but all are DB- or IDE-coupled. We own the IR, so we generate entities directly
  from it with **JavaPoet** — no DB round-trip, no reflection, fully reproducible.
- **IR → Liquibase changelog, deterministically:** Liquibase exposes a Java model
  (`DatabaseChangeLog`, `ChangeSet`, `Change` subclasses like `CreateTableChange`, `AddColumnChange`,
  `AddForeignKeyConstraintChange`, …) and can serialize to XML/YAML/JSON/SQL by file extension. We build the
  changelog object graph from the IR and serialize — **no live database required**.
- **Incremental migrations:** rather than depend on `liquibase-hibernate` diffing a live DB (needs a running
  database, produces whole-schema noise — see liquibase-hibernate issues #164/#188), we **diff two schema IR
  snapshots** (previous committed IR vs new IR) deterministically and emit only the delta change-sets
  (add table/column, drop, alter type, add FK/index, rename via explicit hints). The IR snapshot is committed
  alongside the changelog, so the diff is offline, reproducible, and reviewable.

## 4. The Schema IR (the contract)

The IR is the **single artifact the LLM produces** and the **single input to every generator**. It is a
plain JSON document with a published JSON Schema (used both to constrain the LLM and to validate its output).
It is persisted (`.anvil/schema.ir.json`) and version-controlled — it is the durable source of truth, more
stable than either the SQL or the Java.

Shape (illustrative, not final):

```jsonc
{
  "domain": "Order Management System for a Coffee Shop",
  "version": 3,                         // monotonic, bumped per accepted change
  "dialect": "postgresql",
  "package": "com.egoge.coffee",
  "entities": [
    {
      "name": "Order", "table": "orders",
      "fields": [
        { "name": "id",        "type": "UUID",      "pk": true, "generated": "uuid" },
        { "name": "placedAt",  "type": "TIMESTAMP", "nullable": false },
        { "name": "total",     "type": "DECIMAL",   "precision": 10, "scale": 2, "nullable": false },
        { "name": "status",    "type": "ENUM",      "enumValues": ["NEW","PAID","FULFILLED","CANCELLED"] }
      ],
      "relations": [
        { "kind": "ManyToOne", "target": "Customer", "field": "customer", "fk": "customer_id", "nullable": false },
        { "kind": "OneToMany", "target": "OrderLine", "field": "lines", "mappedBy": "order", "cascade": "ALL" }
      ],
      "indexes": [ { "columns": ["status","placed_at"], "unique": false } ]
    }
  ]
}
```

Design rules:
- **Dialect-neutral logical types** (`UUID`, `DECIMAL(p,s)`, `TEXT`, `TIMESTAMP`, `ENUM`, …) mapped per target
  dialect by a deterministic `DialectMapper`. Default dialect: **PostgreSQL**.
- IR carries only *structure + intent*, never generated SQL/Java — those are derived.
- A stable `id`/name on every entity & field so the **diff engine** can track renames vs add/drop.

## 5. Pipeline (5 stages)

```
 NL text ──▶ [1] SchemaSynthesizer ──▶ Schema IR ──▶ [2] IrValidator ──▶ validated IR
   (LLM, LangChain4j, JSON-schema-constrained)          (deterministic: types, PK/FK integrity,
                                                          name collisions, cycle checks, PII scan)
 validated IR ──▶ [3] LiquibaseGenerator ──▶ changelog.(xml|yaml)   (deterministic, Liquibase model API)
 validated IR ──▶ [4] JpaGenerator       ──▶ @Entity records/classes (deterministic, JavaPoet)
 validated IR ──▶ [5] PersistenceGenerator ──▶ Repository (Spring Data / plain DAO) + Service API
```

- **Stage 1 (only non-deterministic step)** is isolated behind an interface `SchemaSynthesizer` so it can be
  swapped for a fixture in tests and for different providers in prod. Output is **always** re-validated by
  Stage 2 before anything downstream runs; on validation failure → bounded repair loop (feed errors back to
  the model, max N attempts) → hard fail with a readable report if still invalid. **The LLM never writes a
  byte of Java or SQL.**
- **Stages 3–5** are pure functions of the IR — same IR in ⇒ byte-identical output. This is the property the
  test suite pins (golden-file tests).
- **JPA output** targets Jakarta Persistence (`jakarta.persistence.*`), Java records where immutable /
  classes where JPA requires mutability, null-safe mappings, `@Generated` marker.
- **Service/DAO:** two modes, config-selected — (a) Spring Data JPA `Repository` interfaces + a thin
  `@Service` façade (default, dovetails with ai-atlas's `@Service`+`@AgenticExposed` scan), or (b) framework-free
  DAO over `EntityManager` for non-Spring consumers.

### 5.1 Incremental / update flow

```
 existing .anvil/schema.ir.json (v_n)  +  NL "add loyalty points to Customer"
        │
        ▼  [1] SchemaSynthesizer (given prior IR as context) ──▶ proposed IR (v_n+1)
        ▼  [2] IrValidator
        ▼  [Diff] IrDiff(v_n, v_n+1) ──▶ ordered ChangeOp list (ADD_COLUMN, ALTER_TYPE, ADD_FK, RENAME…)
        ▼  [3] LiquibaseGenerator emits ONLY a new incremental changeSet file (id = timestamp+hash)
        ▼  [4/5] JpaGenerator/PersistenceGenerator re-emit affected entities/repositories
        ▼  commit new IR snapshot as v_n+1
```
Renames are the classic ambiguity (drop+add vs rename): the diff engine defaults to safe interpretation and
surfaces ambiguous ops for confirmation (via CLI prompt / MCP tool result flag), never guessing destructively.

## 6. Repo & module layout (mirrors ai-atlas conventions)

```
ai-anvil/
├── settings.gradle.kts                  # Gradle Kotlin DSL, foojay toolchain (as ai-atlas)
├── gradle/libs.versions.toml            # SOLE version authority (align: java 17, jackson, junit…)
├── build.gradle.kts
├── modules/
│   ├── ir/            # Schema IR POJOs + JSON Schema + Jackson (de)serialization. ZERO heavy deps.
│   ├── llm/           # SchemaSynthesizer SPI + LangChain4j impl (Ollama + OpenAI/Anthropic adapters)
│   ├── validate/      # IrValidator, PII scanner, repair-loop orchestration
│   ├── diff/          # IrDiff engine → ChangeOp list (offline, deterministic)
│   ├── gen-liquibase/ # IR/ChangeOps → Liquibase changelog (Liquibase model API)
│   ├── gen-jpa/       # IR → JPA entities (JavaPoet)  ── depends on JavaPoet, like ai-atlas
│   ├── gen-persist/   # IR → Repository/DAO + Service (JavaPoet)
│   └── core/          # AnvilPipeline: wires stages 1-5, the one public façade the surfaces call
├── surfaces/
│   ├── cli/           # picocli standalone CLI  → the deterministic tool for hook scripts
│   ├── mcp-stdio/     # STDIO MCP server (MCP Java SDK) wrapping core  → Claude Code / PI.dev
│   └── intellij/      # IntelliJ plugin wrapping core (phase 4)
└── demo/              # "Coffee Shop OMS" & "Kindergarten Billing" worked examples + golden files
```

Module dependency rules (non-negotiable, ai-atlas style):
- `ir` → zero framework deps (Jackson only).
- `llm` → depends on `ir` + LangChain4j; **the only module allowed to touch a model**.
- `gen-*` → depend on `ir` (+ JavaPoet / Liquibase) — **never** on `llm`. Deterministic by construction.
- `core` → depends on all `modules/*`, exposes `AnvilPipeline`. **Spring-free.**
- `surfaces/*` → depend on `core` only. Adding a surface never touches generation logic.

## 7. Harness integration surfaces (the whole point)

One core, three thin surfaces — so "portable to IntelliJ + usable by Copilots" is a packaging concern, not a
rewrite:

1. **CLI (`anvil`)** — picocli. Subcommands: `anvil init "<domain description>"`,
   `anvil update "<change request>"`, `anvil generate` (re-run deterministic stages from committed IR),
   `anvil diff`. JSON-in/JSON-out mode (`--json`) so **hook scripts** can call it deterministically. This is
   the primary "deterministic tool" artifact for the thesis.
2. **STDIO MCP server (`mcp-stdio`)** — a real standalone process (net-new vs ai-atlas's SSE-in-Spring model),
   registered in a copilot's `.mcp.json` as `{"command":"java","args":["-jar","anvil-mcp.jar"]}`. Exposes
   tools: `anvil_design_schema`, `anvil_update_schema`, `anvil_generate_persistence`, `anvil_diff`. Tool
   results return the IR + file manifest so the agent can review before writing. Uses the MCP Java SDK
   directly (not Spring AI) to stay Spring-free and process-spawnable.
3. **Claude Code hook** — a documented `PostToolUse`/manual hook shelling to the CLI `--json` mode, showing
   the "deterministic tool wrapped by a hook script" pattern the user called out.
4. **IntelliJ plugin (phase 4)** — action + tool window over the same `core`; because `core` is Spring-free
   and dependency-light this is wiring, not new logic.

**Handoff to ai-atlas:** ai-anvil generates the `@Service` + entities; the developer annotates services with
ai-atlas's `@AgenticExposed`/`@AgenticEntity`; ai-atlas's processor then synthesizes REST/MCP/OpenAPI. We will
document this seam and (optionally, phase 3) have ai-anvil emit service stubs *pre-annotated* with ai-atlas
annotations when its (optional, compile-only) annotations jar is present.

## 8. Tech stack & version alignment

Align to ai-atlas `libs.versions.toml` where shared; add new:

- **Java 17** (matches catalog), Gradle Kotlin DSL, foojay toolchain resolver.
- **LangChain4j** (latest 1.x) — `langchain4j`, `langchain4j-ollama`, `langchain4j-open-ai` (+ optional
  `-anthropic`).
- **Liquibase** core (latest 4.x) — model API only, no Maven/Gradle plugin dependency at runtime.
- **JavaPoet** (Palantir `com.palantir.javapoet` 0.6.0 — same as ai-atlas) for all Java generation.
- **Jackson** 2.18.x (align with catalog) for IR (de)serialization + JSON Schema.
- **picocli** for CLI; **MCP Java SDK** (`io.modelcontextprotocol.sdk`) for STDIO server.
- **Jakarta Persistence API** (provided-scope) for entity annotations; Spring Data JPA API only where
  generating Spring repositories.
- **Testing:** JUnit 5, AssertJ (catalog), **golden-file** tests for deterministic stages, a
  `FixtureSchemaSynthesizer` to test the pipeline with **no** live model, and (phase 2) Testcontainers to
  actually run generated Liquibase changelogs + boot generated entities against real PostgreSQL.

## 9. Phased roadmap

| Phase | Deliverable | Exit criteria |
|-------|-------------|---------------|
| **0 — Scaffold** | Repo, Gradle multi-module, `libs.versions.toml`, `ir` module + JSON Schema, `FixtureSchemaSynthesizer` | `./gradlew build` green; IR round-trips JSON; schema validates |
| **1 — Deterministic core** | `gen-liquibase`, `gen-jpa`, `gen-persist`, `core` pipeline (stages 2–5) driven by a hand-written fixture IR | Coffee-Shop fixture → changelog + entities + repo + service; golden-file tests pass; **generated code compiles** |
| **2 — LLM front (stage 1)** | `llm` module: LangChain4j `SchemaSynthesizer` on Ollama, JSON-schema-constrained + validate/repair loop | `anvil init "Coffee Shop OMS"` end-to-end with a local model; Testcontainers applies changelog to PostgreSQL and boots entities |
| **3 — Incremental + surfaces** | `diff` engine, `anvil update`, CLI + STDIO MCP server + hook doc | `anvil update` emits delta changeSet only; MCP server usable from Claude Code via `.mcp.json`; ai-atlas handoff documented |
| **4 — IntelliJ + polish** | IntelliJ plugin, external-provider adapters, docs site, publish to Maven Central under `com.egoge` | Plugin runs pipeline in-IDE; both demos (Coffee Shop, Kindergarten Billing) reproducible |

Recommended first cut for a convincing thesis demo: **Phases 0→2** (NL → running PostgreSQL schema + compiling
JPA layer, all deterministic below stage 1) before investing in the three surfaces.

## 10. Risks & open questions

- **Local-model reliability on schema constraint.** Small models drift. Mitigation: validate+repair loop,
  recommend a capable local model, external fallback. *Open:* which local model to standardize the demo on?
- **Rename detection in the diff engine.** Inherently ambiguous. Mitigation: safe-default + surface for
  confirmation; consider optional stable field IDs the LLM must preserve.
- **Entity/service generation vs the ai-atlas seam.** *Open:* should generated services be pre-annotated with
  ai-atlas annotations (tighter coupling, better demo) or annotation-free (cleaner independence)? Leaning
  annotation-free by default, opt-in pre-annotation.
- **DAO/Service scope creep.** Keep generated service methods to CRUD + finders derived from the IR; anything
  richer is the developer's job (and ai-atlas's exposure job). Resist LLM-drafted business logic.
- **MCP Java SDK STDIO maturity** for a spawn-per-call model — validate early in phase 3.

### <a name="naming"></a>Naming
`ai-anvil` is provisional. It fits the family metaphor (ai-**atlas** synthesizes the API surface; ai-**anvil**
is where the schema/persistence layer is deterministically forged). Alternatives: `ai-forge`, `atlas-schema`,
`schema-forge`. **Decision needed from user.**
